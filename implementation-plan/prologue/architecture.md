# Пролог: устройство проекта и контракты систем

**Предложение, не существующий код.** Ниже конкретная схема для кандидата Godot + GDScript; при выборе другого движка сохраняются обязанности/данные, но не названия узлов. [Этапы](plan.md) задают, когда появляется каждая система; не создавать все папки и пустые обёртки заранее.

## Сцены и модули

Последнее требование автора: прямой основной маршрут 500 м, интерактивные зоны по бокам, компактная карта с текущими метрами без спойлеров; не генерировать отдельные ветвящиеся дороги. Возврат к Стинту остаётся частью сцены. Визуальные состояния кота/окружения отделять от игровой логики: стоящий кот неподвижен, ветер проходит с задержками ([анимации](../../ideas/prologue/animation/plan.md)).

| Будущая область | Содержимое и ответственность |
| --- | --- |
| `game/scenes/prologue/` | Главная сцена маршрута и зоны лесного старта/озера/фермы; выход из дома не показывается, фиксированные сюжетные места отделены от случайных встреч |
| `game/actors/player/` | Контроллер перемещения, визуальная часть кота, взаимодействие. Для 2.5D: CharacterBody3D + спрайт; для 2D: CharacterBody2D. Только выбранный вариант |
| `game/systems/needs/` | Расход/восстановление утверждённых нужд, временные эффекты кофе и травмы отдельно от базовых характеристик |
| `game/systems/inventory/` | Идентификаторы предметов, количество, экипировка/карта/зонтик, атомарный обмен и перенос лута |
| `game/systems/story/` | Явные этапы пролога, условия переходов, журнал однократных эффектов; без расчёта физики/рендера |
| `game/systems/save/` | Проверка права записи/загрузки, версия, снимок, безопасная запись и диагностика повреждения |
| `game/systems/world/` | Часы/погода/укрытия, координата маршрута, устойчивый набор случайных встреч |
| `game/actors/npc/` | Общие взаимодействия/бой и небольшие поведения отдельных ролей; спутница/свинка — отдельные компоненты по необходимости |
| `game/minigames/` | Четыре независимые сцены: свиньи, стрим, рыбалка, кража; единый небольшой контракт входа/выхода |
| `game/ui/` | HUD, карта, инвентарь, диалоги, пауза, настройки, загрузка; отображают данные, не выдают награды самостоятельно |
| `game/data/` и `game/tests/` | Ресурсы/тексты/баланс отдельно от поведения; проверки правил и интеграционных переходов |

Не делать глобальными все системы. Корневая сцена владеет текущим прохождением и передаёт зависимости. Глобальными оставлять лишь действительно межсценовые сервисы при необходимости. Локальные сигналы вместо общей шины с неотслеживаемыми побочными эффектами. Граница ~300–500 строк — повод проверить обязанности, не нарезать файлы искусственно.

**Будущее управление, запрос 07.09.2026:** B открывает инвентарь; переназначение доступно в настройках. Поведение привязывать к действиям, подсказки — к текущим назначениям; пользовательские настройки хранить отдельно от сюжетного снимка. P-телефон нужен только основной игре. В лаборатории P сейчас пауза, отдельной системы настроек ещё нет. [Контракт и проверки](../../ideas/common/design/mechanics/interaction/plan.md).

## Данные и переходы

Имена и тексты для игрока не служат ID. Сохранить существующие номера сцен С1–С9; создать отдельные технические ID пролога, не занимая E01–E16 основной игры. Идентификатор выданной награды уникален в пределах прохождения. Источник авторского решения указывать в описании данных; открытая сцена не становится каноном из-за заполненного ресурса.

Минимальные группы состояния:

- Прохождение: `run_id`, имя, режим, `content_version`, seed и состояние генераторов случайности.
- Мир: позиция/зона, координата вдоль маршрута, максимальная достигнутая координата, часы/погода, созданные НПС, оставшийся мировой лут.
- Игрок: нужды, базовые характеристики, временные эффекты, инвентарь, экипировка, спутница/свинка и их состояние.
- История: этап каждого узла, известные сведения, принятые решения, право возврата к дому, результат пролога, применённые эффекты.
- Активное действие: ID диалога и узла, текущая мини-игра и её восстановимые параметры, состояние перехода/титров.

Не начислять прогресс маршрута за круги. При возврате 189 → 100 м и обратно позиция меняется, достигнутые сюжетные рубежи не срабатывают повторно. Для случайных встреч хранить не только seed: выбранные ID, позиции, завершение и взятый лут, чтобы изменение генератора не пересоздало их при загрузке.

### Узел Братишкина: что нельзя зашить догадкой

| Действие | Необходимая проверка | Установленный результат / пробел |
| --- | --- | --- |
| Сообщить о папке | Герой действительно нашёл её | Поход со Стинтом, разбирательство, уход и запрет возврата; способ блокировки надо поставить в сцене |
| Не сообщать | Не требует возврата к Стинту | Продолжение пути; тайна не раскрыта |
| Получить спутницу | Условия ветки и факт предыдущего получения | Бесплатно на выбор, если не сдаёт; получение не закрывает ветку сдачи (автор, 06.09.2026) |
| Украсть спутницу | Ветка сдачи, доступ к месту | Только до похода со Стинтом и разбирательства; после запрета возврата недоступна (автор, 06.09.2026) |
| Работать | Начало/этап свиной мини-игры | Отдельный исход «остался модерировать»; уйти можно в любой момент, исход — только при доведении работы до конца (автор, 06.09.2026) |
| Уехать на свинке | Свинка украдена либо получена кодом | Пропуск участка, не новый финал; точная точка возвращения и сохранение сюжетных возможностей открыты |

Сначала заполнить эти пробелы с автором, затем составить таблицу переходов и проверить достижимость. Не моделировать три пункта меню как три взаимоисключающих флага, если персонажа можно получить до рассказа.

## Мини-игры, бой, интерфейс

Каждая мини-игра принимает контекст прохождения и умеет начать, остановиться, выдать результат, собрать/восстановить снимок. Результат — успех, ошибка или добровольный выход; смысл для сюжета задаёт вызывающий узел. Повторная рыбалка — новый запуск, а не повторная выдача награды старого. Спутница помогает через тот же контракт, не подделывает ввод и не обходит проверку однократности.

До реализации каждой мини-игры описать: управление; подсказку; условия успеха/ошибки; стоимость попытки; выход; награду; помощь спутницы; сохранение посреди действия. Числа тайминга/баффов — настраиваемые пробные данные, не утверждённый баланс.

У боя отдельные состояния удара, защиты, получения урона и завершения; взаимодействие не должно одновременно запускать разговор и удар. Грабёж переводит ресурсы один раз, при проигрыше — один экземпляр выпавшего лута. Поведение атакованных сюжетных НПС надо согласовать до включения боя рядом с ними, иначе можно потерять обязательный квест.

Ввод через именованные действия: движение в двух осях, взаимодействие, удар, защита, бег, инвентарь, карта, пауза, подтвердить/отмена. ЛКМ/ПКМ для боя — авторское решение; раскладка геймпада и остальных кнопок — предложение для проверки. Фокус меню перехватывает боевой ввод. Телефон не показывать как рабочую функцию пролога.

Пауза останавливает симуляцию; **[канон, 06.09.2026]** время в новелльных диалогах и мини-играх идёт. Один источник игрового времени, а не четыре независимых таймера. Сон создаёт снимок по завершённому переходу, не каждый кадр анимации. Принудительное засыпание не автоматически приравнивается к разрешённому ночному сейву.

## Сохранение без потери и удвоения

Предложенный формат v1: читаемый JSON с явной схемой, простыми значениями и стабильными ID; не сериализовать объекты сцены/исполняемый код. Проверять типы, границы, версию, отсутствующие ресурсы; неизвестную будущую версию отклонять с понятным сообщением. Настройки и профиль достижений отдельно от прохождения. Пролог не переносит состояние в основную игру по решению автора.

Запрос ручной записи на разрешённом режиме обслуживается на границе согласованного шага, в том числе внутри диалога/мини-игры. Обновление решения, предмета и журнала эффекта — одна транзакция в памяти; только затем снимок. На загрузке восстанавливать состояние, не повторно выполнять входные награды узлов. Для боевой/стелс-сцены хранить необходимое состояние противников, обнаружения и тайминга, а не молча перезапускать попытку.

Запись во временный файл → проверка → замена целевого файла с резервной копией. Ошибка диска/прерывание не уничтожают предыдущие снимки. Не обещать одинаковую атомарность всех файловых систем: проверить поведение на целевых ОС. Политика записи проверяется в сервисе, не только скрытием кнопки. На харде разрешены гриб и ночной сон, не ручной/быстрый/выходной сейв. Правила загрузки по режимам сверять с [матрицей](../../ideas/common/design/saves/plan.md).

Финал сначала фиксирует результат/профиль, затем показывает сцену и титры, после чего выполняет авторский автовыход. Запись результата в профиль не создаёт запрещённый снимок позиции на харде. Ранее существующие подходящие сейвы остаются доступными при следующем запуске.
