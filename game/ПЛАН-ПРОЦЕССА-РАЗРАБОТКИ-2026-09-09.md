# План процесса разработки — 09.09.2026

**Статус:** организационный план, не изменение игрового кода. Составлен после ответов автора на предложения по улучшению процесса.

Автор одновременно пишет код локально и работает через Hoplite. Поэтому один файл со всем текущим состоянием может смешать разные версии кода. Ниже разделены общие авторские решения и технические состояния каждой линии разработки.

## ПР1. Контексты разных версий — открыто по деталям

Первоначальное предложение оставить один главный контекст автор отверг. Вместо этого предложена трёхуровневая схема:

1. Корневой `CONTEXT.md` — **общая база**, одинаковая для всех версий: последние решения автора, ограничения канона, ссылки на тематические планы и перечень активных направлений. Не хранить здесь подробный список каждого изменённого скрипта.
2. `game/HOPLITE_CONTEXT.md` — **техническое состояние ветки Hoplite**: ветка/коммит, что реально есть именно в ней, последние проверки, незавершённая работа и предупреждения следующей Hoplite-модели.
3. Корневой `LOCAL_CONTEXT.md` — **техническое состояние локальной версии автора**: ветка/коммит или дата снимка, локальные изменения, проверки и отличия от Hoplite.

Каждый исполнитель сначала читает корневой `CONTEXT.md`, затем только контекст своей версии. Перед переносом изменений между версиями нужно сравнить базовые коммиты и затронутые файлы; нельзя считать одну версию автоматически новее во всём.

Автор снял ограничение на корневые правки 09.09.2026. Корневой `LOCAL_CONTEXT.md` создан как актуальная передача локальной модели; исторический `GLM_CONTEXT.md` сохранён отдельно. Фактические ветку, SHA и рабочее дерево заполняет локальная модель — Hoplite их не выдумывает.

**Решения автора 09.09.2026:**

- локальный контекст обновляет локальная модель/агент;
- в технических контекстах обязательно указывать ветку и полный SHA известного снимка кода;
- перед новым этапом Hoplite проверяет, не изменился ли `main`, и не начинает писать поверх неразобранного расхождения;
- конфликт одного файла между локальной и Hoplite-версиями сначала разбирается ручным планом объединения, без автоматического выбора победителя.

## ПР3. Реестр чисел и статусов — подтверждено

Создать отдельный реестр параметров игрового баланса и маршрута. Для каждого значения хранить:

- идентификатор и назначение;
- текущее значение и единицу измерения;
- статус `канон автора`, `техническое`, `предложение` или `открыто`;
- источник/дату решения;
- затронутые скрипты и тесты;
- требуется ли Deck-проверка ощущения.

Изменение технического числа не становится изменением канона. Каноническое число нельзя менять ради прохождения теста без решения автора.

## ПР4. Разделение dev- и обычной сборки — подтверждено

- Телепорт по метрам, множители скорости, запуск встречи, показ коллизий/FPS и сбросы доступны только при явном dev-флаге.
- Обычная сборка не должна показывать dev-панель, реагировать на её горячие клавиши или сохранять включённые читы.
- Тесты должны проверять оба режима.
- Экспорт/запуск обязан явно сообщать, какой режим активен, без сюжетного текста в интерфейсе игрока.

## ПР5. Источники и лицензии ассетов — подтверждено

Для каждой внешней модели, текстуры, иконки, анимации, музыки, звука и шрифта хранить:

- имя файла/ресурса;
- источник и автора;
- лицензию и обязательную атрибуцию;
- статус `авторский`, `разрешён для релиза`, `только референс`, `временный` или `запрещён для релиза`;
- место использования.

Кодогенерируемые пробы тоже помечать как пробы. Отсутствие найденного запрета не считать лицензией.

## ПР8. Матрица конфликтов режимов — подтверждено

Зафиксировать совместимость основных режимов: обычное управление, пауза, карта, инвентарь, диалог, бой, катсцена, рыбалка, слизарио, свинки, стелс, экран конца и dev-панель.

Для каждой пары определить: разрешено одновременно, приостанавливает нижний режим или запрещено. Автоматические тесты должны покрывать критические запреты: бой+диалог, две мини-игры, управление во время катсцены, награда после конца и dev-команда в обычной сборке.

## ПР10. Приоритеты ошибок — подтверждено

Использовать четыре уровня:

1. **Блокирующая:** потеря прогресса, падение, невозможность продолжить, выход за мир, повреждение сейва.
2. **Высокая:** неправильное управление, сломанный квест/бой/диалог, повторная награда, неверный канон.
3. **Заметная:** плохая камера, скольжение, всплывающие чанки, нечитаемый интерфейс, ошибочный масштаб.
4. **Косметическая:** небольшой визуальный дефект без влияния на управление, смысл и читаемость.

Приоритет не отменяет проработку: косметические проблемы закрываются после стабильности, а не объявляются необязательными навсегда.
